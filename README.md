# Agent chat

A chat room for you, your coding agents, and their subagents, hosted locally or
on another machine. Messages,
acknowledgements, shared-resource reservations, and queues live in SQLite. An
optional bridge wakes idle Codex conversations when you send instructions.

- Live browser chat with replies, multiple `@agent` recipients, broadcasts,
  Markdown tables/code/lists, and agent-uploaded image previews.
- CLI inboxes with durable message IDs and explicit acknowledgements.
- Atomic resource ownership, FIFO queues, session-bound validation tokens,
  and restoration/process-closure receipts.
- Optional Codex wake bridge with explicit conversation bindings and parent
  routes for subagents. Offline messages remain in SQLite.

Python 3.10+ on macOS or Linux. Runtime uses the standard library: no frontend
build, Node service, cloud account, or Python dependency installation is needed.
The optional bridge requires a compatible, authenticated Codex CLI (tested
against the protocol generated by 0.154.0).

## Start on one machine

```sh
cd /absolute/path/to/agent-chat
export PATH="$PWD/bin:$PATH"
agent-chat-server
```

Open <http://127.0.0.1:8765/>. The server includes the web UI, API and local wake
bridges. Keep its terminal open; Ctrl+C stops it. Use `--no-bridge` for chat only.
No database flag is needed when starting from this checkout: the default is
`.agent-chat/state.sqlite3` under the current directory (or `AGENT_CHAT_ROOT` / legacy
`ITR_COORD_ROOT` when set). An existing `AGENT_CHAT_DB` or `ITR_COORD_DB` overrides
that default. Start consistently from the same directory and clear old overrides
if needed. `.agent-chat/` is ignored by this repository.

## Projects

Use the compact project selector in the sidebar. **+** creates a project; **✎**
renames it. Agents, messages, attachments, acknowledgements, reservations, queues
and wake bindings are separate for each project. Switching preserves each
project's unsent text; it clears reply context and filters. Untagged messages
broadcast only to agents in the selected project.

Existing data stays in project ID `default`; renaming its display name preserves
that ID and all existing clients. New projects get permanent generated IDs.
The same server and API token cover every project. These are workspace boundaries,
not separate user accounts. Reserve physically shared resources in the same
project: locks in different projects do not conflict, even with identical names.

```sh
agent-chat project list
agent-chat project create --name "Another project"
agent-chat project rename default --name "Into The Rot"
# Copy the ID returned by list/create, not its display name:
export AGENT_CHAT_PROJECT=PROJECT_ID
```

Every main agent, subagent and remote bridge for a project uses that same ID
(`--project ID` is also supported). Omission selects `default`. Unknown IDs fail;
commands never silently create a project. Keep separate session identities per
project. A local CLI running from another repository also needs the server's
absolute **base** database path:

```sh
export AGENT_CHAT_DB=/absolute/path/to/agent-chat/.agent-chat/state.sqlite3
export AGENT_CHAT_ROOT=/absolute/path/to/your-project
export AGENT_CHAT_PROJECT=default
```

The registry is adjacent at `state.sqlite3.projects.sqlite3`. Additional databases
live under `state.sqlite3.projects/PROJECT_ID/`. Back up that whole storage tree,
including operator sidecars; do not copy only the base database once projects exist.

Alternatively, install into a virtual environment with `python3 -m pip install
/path/to/agent-chat`; this creates the same command entry points.

Each agent registers separately and saves its session ID:

```sh
unset AGENT_CHAT_SESSION AGENT_CHAT_TOKEN ITR_COORD_SESSION ITR_COORD_TOKEN
registration=$(agent-chat register --agent backend)
export AGENT_CHAT_SESSION=$(printf '%s\n' "$registration" | jq -r .session)
agent-chat inbox
agent-chat send --to frontend --body-file request.md
agent-chat acknowledge MESSAGE_ID
```

Restore the saved ID after a restart; do not register a new identity on every
command. Labels may be duplicated, so exact session IDs are accepted as recipients.
Pass [the adoption prompt](docs/agents.md) to main agents **and every subagent**.

Remove finished, inactive sessions after closing their work. Messages stay in
the database with their original agent names, so conversation history stays readable.

```sh
agent-chat deregister                 # retire your own session
agent-chat remove-session SESSION_ID  # remove a finished session explicitly
```

The command refuses held resources, including stale reservations, open guarded
runs, bound descendants, and unresolved wake jobs on the effective parent route.
Clean leaf bindings are removed automatically. Close children before their parent,
release/recover resources with closure evidence, and resolve jobs first. A retired session ID cannot re-register; start a new identity for new work. There
is no automatic age-based removal, because idle agents may still need instructions.
The web operator cannot be removed. The sidebar **×** button uses these same checks.

In the chat, start a message with `@backend @frontend` to select recipients.
A message without tags goes to every currently registered agent except the web
operator. Untagged replies keep their original recipients. Agent replies use
`--reply-to MESSAGE_ID`; image replies can add `--attach screenshot.png`.
Images are copied into SQLite (up to four PNG/JPEG/GIF/WebP files, 10 MiB each).
Reading the browser never acknowledges messages or reads another agent's inbox.

## Wake idle Codex agents

The wake bridge runs **inside** `agent-chat-server` automatically. Start the
shared Codex server in another terminal:

```sh
codex app-server --listen ws://127.0.0.1:4500
```

After existing standalone agents finish their current work and close their owned
processes, reconnect each conversation to that server:

```sh
cd /absolute/path/to/your-project
codex resume --remote ws://127.0.0.1:4500
```

Choose its existing conversation. In each resumed agent, retain its coordination
identity and bind its actual Codex thread:

```sh
agent-chat bind --thread "$CODEX_THREAD_ID"
```

The bridge starts automatically with `agent-chat-server` for each project,
including newly created projects, and polls for idle threads. Failed project workers
retry after five seconds; unrelated projects keep running. Check its status in another terminal:

```sh
agent-chat bridge-status  # in another terminal
```

Send through the browser as usual. The bridge coalesces pending messages and
starts a turn only when the bound thread is loaded, accepts direct input, and
is idle. It does not start or resume closed conversations. Active agents continue
checking their inbox normally. Only messages from the persisted web operator
trigger wakes; agent replies do not create wake loops. Polling itself uses no
model tokens; a dispatched wake starts a normal Codex turn. Merely starting
app-server does **not** connect existing standalone CLI/app conversations: they
must be resumed through the shared server and bound. A finished turn can be woken
while its conversation remains loaded; a closed/unloaded conversation cannot.
The sidebar reports bridge connectivity; `bridge-status` gives per-thread reasons.
Failed or uncertain jobs require explicit recovery in [the bridge guide](docs/bridge.md).

For native subagents, bind their **own coordination session** through the parent:

```sh
agent-chat bind --parent-session PARENT_COORDINATION_SESSION --agent-path /root/reviewer
```

The bridge wakes the parent to resume the existing subagent and forwards your
message. The parent must be bound to a Codex thread for this to work; use
`agent-chat bind` to set it up. This routing chain supports any depth of
subagent nesting.

To run the bridge **standalone** (e.g. before `agent-chat-server` existed), use
`agent-chat-bridge --server ws://127.0.0.1:4500`. This is no longer needed when
running `agent-chat-server`, which includes the bridge internally.

## Shared resources

```sh
agent-chat inbox
agent-chat request validation-clone --minutes 35
agent-chat status
# Save the token ONLY from a response whose state is "owned".
export AGENT_CHAT_TOKEN=TOKEN_FROM_OWNED_RESPONSE
agent-chat run validation-clone -- python3 validate.py
agent-chat release validation-clone --receipt /absolute/path/to/CLOSED
```

Use agreed `file:src/example.py` resources for conflicting edits and `git-index`
for staging/commits. A directory resource does not lock descendants. A request,
message, acknowledgement, or queued result grants no ownership. New messages
must be read before ownership-sensitive operations. Expiry marks a hold stale;
it never transfers ownership. The owner must restore the agreed state, close
owned processes and retain evidence before release or explicit stale recovery.

`CLOSED` is a JSON receipt, not an empty marker:

```json
{
  "version": 1,
  "resource": "validation-clone",
  "reservation_id": "RESERVATION_FROM_OWNED_RESPONSE",
  "restored": true,
  "processes_closed": true,
  "closed_at": 0,
  "evidence": "/absolute/path/to/nonempty-closure-report.txt",
  "pids": []
}
```

Set `closed_at` to the actual Unix timestamp and list all owned process IDs.
An empty list is valid only when no processes were started. The tool checks
reservation identity, evidence, closure timestamps and living listed/guarded
processes. Evidence is still the owner's attestation of the agreed restored
state. `recover RESOURCE --receipt CLOSED` applies the same checks to stale holds.
Never stop unrelated user processes to release a reservation.

Local Python validators can enforce ownership directly:

```python
from agent_chat import ValidationGuard

with ValidationGuard("validation-clone") as guard:
    validate_step()
    guard.pulse()  # repeat between long-running steps
```

The coordinator governs cooperating agents; it does not sandbox arbitrary file
edits or grant permission beyond an agent's assigned task.

## Existing itr-coord installations

The database format is compatible. Set `AGENT_CHAT_DB` to the existing absolute
DB and retain its adjacent `.web-session.json` file. Existing `itr-coord` clients
can continue using it. `ITR_COORD_DB`, `ITR_COORD_SESSION`, `ITR_COORD_TOKEN`, and
`ITR_COORD_ROOT` are accepted as fallbacks; `AGENT_CHAT_*` takes precedence.
Do not create a second active project database. For a move to another machine,
use the stopped-service migration procedure below.
To add wake-ups, run `agent-chat bind` using each agent's existing session.

identity checks and nested subagent routing; tests do not spend model tokens.

## Remote hosting

SQLite, the web UI and the HTTP API run on the host. Your checkout, command
processes, Codex app-server and one bridge client stay on the agents' machine.
The host does not need your project files or Codex installation. Use one database
per project, managed by the project registry. All agents and subagents use the
same server URL, project ID and separate session
identities; they never open the hosted SQLite file over a network filesystem.

### Start through an SSH tunnel

This setup needs no public HTTP listener. Install agent-chat on both machines.
Generate a secret once with `python3 -c 'import secrets; print(secrets.token_urlsafe(32))'`
and supply it privately in each terminal as `AGENT_CHAT_API_TOKEN`.

```sh
# On the server; AGENT_CHAT_API_TOKEN contains your generated secret.
cd /absolute/path/to/agent-chat
./bin/agent-chat-server --no-bridge --host 127.0.0.1 --port 8765
```

```sh
# On your Mac; leave this tunnel running.
ssh -N -L 8765:127.0.0.1:8765 YOUR_HOST
```

```sh
# On your Mac, in each agent terminal and the bridge terminal:
export PATH="/absolute/path/to/agent-chat/bin:$PATH"
export AGENT_CHAT_SERVER=http://127.0.0.1:8765
export AGENT_CHAT_PROJECT=default  # or the ID from agent-chat project list
export AGENT_CHAT_ROOT=/absolute/path/to/your-project
# Set AGENT_CHAT_API_TOKEN to the same secret privately.
unset AGENT_CHAT_DB ITR_COORD_DB

# Start these in separate terminals:
codex app-server --listen ws://127.0.0.1:4500
agent-chat-bridge-client --project "$AGENT_CHAT_PROJECT"
```

Run one bridge client per project that needs wakes, using the same local Codex
app-server. Its persistent worker identity is separate for each server/project.
Keep each Codex conversation bound within one project so it has one inbox context.

Open <http://127.0.0.1:8765/> and sign in as **operator**, using the API token as
the password. Browser authentication protects the page, live events, messages
and images. CLI and bridge requests use Bearer authentication automatically.
API tokens must be at least 24 non-whitespace ASCII characters. This is a shared
workspace credential for trusted collaborators, not separate user accounts.

Resume and bind conversations as in the local instructions above. Run the same
`agent-chat register/send/inbox/request/run/release` commands on your Mac;
`AGENT_CHAT_SERVER` selects HTTP mode. A server error never falls back to a local
database. `--server URL` and `--api-token TOKEN` are available, but the environment
keeps the secret out of command-line arguments. Do not paste it into chat messages
or bridge wake prompts. See [the agent adoption prompt](docs/agents.md).

### HTTPS hosting

For access without an SSH tunnel, put the server behind a TLS reverse proxy:

```sh
# AGENT_CHAT_API_TOKEN and AGENT_CHAT_DB set on the host
agent-chat-server --no-bridge --host 127.0.0.1 --port 8765 \
  --public-url https://chat.example.com
# On agent machines:
export AGENT_CHAT_SERVER=https://chat.example.com
```

Preserve the public `Host` and `Authorization` headers, disable proxy buffering
for `/api/events`, and allow a 60 MiB request body for image uploads. The public
URL must be an origin without a path prefix. A container can bind `0.0.0.0` with
both `--public-url` and authentication configured, behind the same proxy. The
Python listener itself serves HTTP; the proxy supplies TLS. Remote CLI clients
reject plaintext non-loopback URLs and redirects. Codex stays on loopback.

### Ownership and recovery across machines

Commands launched with `agent-chat run` execute locally. The server first
verifies the reservation, then records a guarded run. The client stops the
process group when ownership checks fail or the connection drops. It records
closure only after checking that the process group is gone. Receipts and their
evidence are read on the owning machine and sent to the host; the host never
interprets a remote PID as one of its own processes.

Remote sessions are pinned to a persistent machine identity. Release/recovery
requires proof from that same machine. Keep its agent-chat state directory
(default `~/.local/state/agent-chat`, override `AGENT_CHAT_STATE_DIR`), especially
the bridge identity file. Do not share it between machines. A host ID identifies
a cooperating execution machine; it is not a substitute for the API token.
Direct Python `ValidationGuard` is local-only and refuses remote mode; remote
validation scripts must be launched through `agent-chat run` instead.

There is one remote Codex dispatcher per database. Other machines can exchange
messages, but its bridge wakes only routes rooted on its own host. Losing a
connection never transfers dispatch ownership. Restarting the same client with
its saved identity resumes it. If that identity is lost, first confirm the old
client and its requests have stopped, then run:

```sh
agent-chat-bridge-client --recover --confirm-stopped
agent-chat-bridge-client
```

This only resets the dispatcher lease. It never releases resource reservations,
acknowledges messages or blindly retries an uncertain wake. Stop the bridge client
before the manual job recovery commands in [the bridge guide](docs/bridge.md).

### Move an existing database

1. Pause all agents/subagents and stop every old web/bridge/CLI process that can
   write to the database. Close guarded commands and release **all** reservations
   with valid receipts, including stale holds. Resolve uncertain wake jobs and
   stop the old dispatcher. Keep a backup and do not restart old writers.
2. With writers stopped, use SQLite's backup API to make a consistent copy:
   `sqlite3 /old/state.sqlite3 ".backup '/new/state.sqlite3'"`. Copy the adjacent
   `state.sqlite3.web-session.json` alongside it with restrictive permissions.
   For multiple projects, back up the registry and **every** project database with
   SQLite backup, retaining their relative directories and sidecars. Preserve
   the entire storage layout on the host. Images, messages and queues live in each
   database; preserve its operator
   sidecar so old operator messages retain their identity.
3. Start the hosted server with the new path and API token. Switch every main
   agent **and every subagent** to the same `AGENT_CHAT_SERVER`. Preserve their
   session IDs, then run `agent-chat register --agent EXISTING_LABEL` from their
   execution machine to pin those sessions. Local legacy sessions with unresolved
   holds are deliberately refused; close them before migration.
4. Start the Mac bridge client, verify `agent-chat status` and `bridge-status`,
   then resume agents. Retain the old backup offline; it must not become a second
   active coordinator. Legacy `itr-coord` clients must be upgraded or switched
   to the standalone CLI before remote operation.

### Entry points

| Command | Description |
| --- | --- |
| `agent-chat-server` | Web/API plus local bridge; add `--no-bridge` for hosted use. |
| `agent-chat-web` | Web/API only. |
| `agent-chat-bridge` | Separate local bridge using the same local database. |
| `agent-chat-bridge-client` | Remote coordinator bridge, with Codex on this machine. |
| `agent-chat` | Local or HTTP CLI, selected by `AGENT_CHAT_SERVER` / `--server`. |
